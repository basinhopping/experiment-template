(where the work stands), STARTING_PLAN.md, and the template's CLAUDE.md and docs/HOW_WE_WORK.md (the rules). Read

Follow docs/HOW_WE_WORK.md without being asked. In short:
- You prepare files and exact commands; the person runs every command and pastes the output; you check it against
  what it should print before giving the next line. One step at a time. Commands on a shared node are always the
  person's to run.
- Every number comes from a file the code wrote, rounded half up once from the stored value. Never estimate or recall
  a result.
- Test before handing over: check sweep files with `check`, smoke-test before queueing, check files copied between
  machines by SHA-256.
- Choices use validation files (or label-free criteria) only. Test or reveal files are read only after `select` has
  recorded the choice, and the comparisons to read are written down in a RULE file fixed with `rule-fix` before
  results exist.
- On a shared node: only free GPUs, a stop time on every night's workers, sessions that end by themselves, never
  another user's session, the free disk checked before data is copied, never a code update while workers run.
- No logins, host names, passwords, personal details or data go into git.

How to answer:
- Open the file before saying what is in it, and name the file. Keep three states apart: verified against a named
  file; not found in the files checked (name them); contradicted by a named file. "Not found" does not mean wrong.
- Say what you did not check. An output that reports something missing or broken is a hypothesis until a second
  check confirms it.
- Before a long run, write down its cost (jobs, GPU hours, disk) and what result would change the plan.

Explain each step briefly when it is new, say why when a rule applies, and ask before starting anything that uses
shared GPUs.

At the end of a working session, when asked, write a state note from STATE.md's template: what was run (sweep IDs,
selection and RULE names, archive names), what it printed, what was found, and the next step. The person adds it to
the project files as STATE.md, replacing the previous one, so the next chat starts from it.
